# TAU1302 limitations

How device-independent configuration is realized on the Allystar
TAU1302 (HD9310), relative to perfect realization of the full model
(`SEMANTICS.md`). Measured on firmware 3.018.f3667a12 (2026-07-03,
UART at 115200). Perfectly-realized behavior is not listed.

## Starting state

Factory defaults except the RTCM broadcast-ephemeris targets off,
saved to NVM; `setup/tau1302.sh` establishes it. The ephemeris output
matters: it is outside the model vocabulary, so every RTCM request
turns it off and no request can turn it back on, which means gpshwtest
can restore what it finds only if the starting state does not include
it. (The factory state - the shipped RTCM table with ephemerides
emitting, the all-zeros CFG-PPS block, and the narrower signal
selection - is otherwise kept.)

## Signals

Supported signal set (L1/L2 dual band):

| GNSS | Signals |
|------|---------|
| GPS  | L1 C/A, L2C |
| GAL  | E1 |
| GLO  | L1, L2 |
| BDS  | B1I, B2I |
| QZSS | L1 C/A, L2C |

- This unit's silicon COUPLES: writing a Galileo E5 bit it lacks
  switches Galileo E1 on (found by gpshwtest's syntax-equivalence
  check). satpulse therefore intersects requests with the
  identity-deduced plan before writing, so unsupported bits never
  reach the wire on known hardware; the coupling remains latent for
  unknown models, where the verify readback reports whatever the
  silicon did.
- The unit ships with a selection narrower than its capability:
  GLONASS and QZSS are disabled in its as-found mask.

## Properties

Same shape as the other two units: no antenna cable delay (CFG-PPS
Offset is factory calibration, 0 ns on this unit); ECEF-only fixed
position storage at 0.01 m quantum with no stored accuracy; float32
minimum elevation; no pulse alignment or timing constellation; the
active UART is not identifiable.

## Message output

- `tp`, `leap` (announcement date), and per-signal `sig` deliver
  nothing.
- RTCM MSM4 and MSM7 emit per enabled constellation. Unlike the
  TAU951M, this unit emits a 1005 ARP even with a zero fixed position.
- The unit SHIPS with RTCM broadcast ephemerides (1019/1042/1046 for
  its enabled constellations) and MSM7 enabled and emitting. Every
  RTCM request turns the ephemeris targets off along with the unnamed
  group members, and no request can re-enable them (they are the
  group's *other* element, beyond the model vocabulary; CLI exposure
  of `RTCMMsgOther` is #348). The characterization starting state
  therefore excludes them (see Starting state above). The shipped
  RTCM table and the all-zeros CFG-PPS block are this unit's factory
  state (verified 2026-07-05 by rate polls and CFG-PPS readback), so
  a factory reset re-arms the ephemeris output and the setup script
  must be re-run after one.
- Raw output is the single RXM-DUMPRAW switch (~2.3 KB frames).

## Receiver defects

- CFG-PPS handling of a zero duty cycle is ERRATIC at the register
  level: after the same byte-identical ACKed write a later readback
  sometimes shows the write had no effect (the old width stays), and
  sometimes shows the whole CFG-PPS block cleared to zeros (which is
  also this unit's factory register state - period, GPIO, everything
  zero, unlike the other two units, whose factory CFG-PPS values
  survive a factory reset). The incidence drifts: on 2026-07-03 the
  width-to-0 restores passed; on 2026-07-13 they failed on every
  attempt across six runs (the last probed width, 0.1 or 0.25, stayed
  in the register), so characterization runs on this unit currently
  fail the width restore every time, and a disruptive run's recovery
  save-all persists the stuck value, failing the NVM consistency
  checks too. Recovery from the stuck value is an NVM reload. Per the semantics satpulse reports the
  values the receiver ACCEPTED, with no verify roundtrip to police
  the defect, so after a pulse-off request this unit's stored state
  may differ from the reported achieved values - visible to anyone
  who reads the property back. Width probing cannot be made
  run-to-run deterministic under --disruptive for the same reason.
  What the PPS pin itself does in either state was not observed (no
  timing instrumentation); all time-pulse findings on all three
  units are CFG-PPS register readbacks.
- After a cold or factory reset, RTCM output (ephemerides and MSM)
  resumes only as satellites are re-acquired and re-decoded, so
  emission checks within a normal observation window report messages
  missing that are merely not yet resumed. Disruptive characterization
  runs on this unit report restore mismatches for this reason.

## Testing notes

Starting-state running configuration (post setup/tau1302.sh): NMEA
GGA, GSA, GSV, RMC, ZDA at 1 Hz (TXT off); mobile mode; GPS L1+L2C,
BDS B1I+B2I, GAL E1 selected (GLONASS/QZSS off); RTCM MSM7 at rate 1,
ephemerides/MSM4/ARP at 0. CFG-CFG load (action 1) actually works in
place on this unit, unlike the other two where it is acknowledged and
ignored - reload is realized as a soft reset everywhere regardless. A
full non-disruptive run takes about 20 minutes and leaves the
receiver as found.

The RTCM baseline lives in the NVM rate table (save bit 1), and
probing runs soft-reset the unit (reload probes), which reloads NVM
into the running rates. A session that saves NVM must therefore save
the starting-state rate table back and VERIFY with a soft reset;
restoring only the running rates leaves a time bomb every later
reload re-arms. This happened once: a disruptive session persisted
MSM7 rates 0, the running-only restore hid it, and the next probing
run's reload probes resurfaced it as not-left-as-found failures
(repaired 2026-07-03 with save + reset-verified readback).
