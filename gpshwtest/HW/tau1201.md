# TAU1201 limitations

How device-independent configuration is realized on the Allystar
TAU1201 (HD8040D), relative to perfect realization of the full model
(`SEMANTICS.md`). Measured on firmware 3.018.aab95e7 (2026-07-03, UART
at 115200). Perfectly-realized behavior is not listed.

## Signals

Supported signal set (L1/L5 dual band):

| GNSS | Signals |
|------|---------|
| GPS  | L1 C/A, L5 |
| GAL  | E1, E5a |
| GLO  | L1 |
| BDS  | B1I, B2a |
| QZSS | L1 C/A, L5 |

- satpulse intersects requests with this identity-deduced plan before
  writing; the CFG-NAVSAT silicon also clamps any written mask to this
  set (a full or all-ones mask reads back as exactly this), and the
  achieved set comes from the post-set verify poll. No
  constellation-count limit; no coupled signals observed on this unit
  (unlike the TAU1302). A zero mask is accepted and applied.
- SBAS and NavIC requests intersect to nothing: the bits exist in the
  mask vocabulary but not in this unit's plan.
- GLONASS L1 is in the clamp set but the unit tracked no GLONASS
  satellites at the test site; that is reception, not configuration.

## Properties

- Antenna cable delay does not exist. The CFG-PPS Offset field (530 ns
  factory value on this unit, surviving factory reset - evidently
  calibration) is deliberately not mapped onto it and is preserved by
  pulse writes. Time-pulse behavior here and below is CFG-PPS register
  readback; the physical pulse on the PPS pin was not observed (no
  timing instrumentation on this setup).
- Fixed position is ECEF-only in storage: an LLH set is converted by
  satpulsetool and stored (and read back) as ECEF centimeters
  (quantum 0.01 m). There is no stored position accuracy: whatever
  accuracy a set requests, readback reports zero.
- Minimum elevation is stored as a float32 in radians, so readback
  carries ~1e-7 degree rounding.
- Time pulse alignment (GNSS vs UTC) and timing constellation have no
  carrier and are absent.
- The active UART is not identifiable (`--show-port` reports the baud
  only when asked; the port name is never reported), and a CFG-PRT
  baud set always switches the port it arrives on.

## Message output

- Time-of-pulse (`tp`) delivers nothing: the protocol has no
  pulse-time message (the POSTIME message was removed from the
  protocol in 2017). End-of-epoch is delivered via iTOW tracking.
- Leap-second information (`leap`, the announcement date) delivers
  nothing: NAV-TIME carries only the current UTC offset, and no
  message announces leap events.
- Per-signal satellite information (`sig`) delivers nothing:
  NAV-SVINFO is one row per satellite even for dual-band satellites.
  Per-satellite (`sat`) delivers.
- RTCM output does not exist on this unit: every 0xF8 CFG-MSG target
  is refused, so RTCM requests achieve nothing (shown as absence, no
  error). The capability flags still advertise RTCM for the vendor;
  this unit's absence is per-receiver truth.
- Raw output (`obs`/`nav`) maps to the single RXM-DUMPRAW switch,
  which emits one undocumented RXM-RAW (0x02 0x57) frame of ~2.2 KB
  per second. Both raw kinds enable the same stream.

## Testing notes

As-found running configuration: NMEA GGA, GSA, GSV, RMC, ZDA, TXT at
1 Hz; mobile mode; the full supported signal set; PPS 1 s period, 10%
duty, rising, GPIO 13, offset 530 ns. The unit persistently reports
`$GNTXT ... ANT_OPEN` while tracking ~25 satellites with a genuine
fix - an antenna-sense oddity of this board, not a configuration
problem. A full non-disruptive run takes about 20 minutes and ends
with the receiver restored as found.
