# ZED-X20P limitations

How device-independent configuration is realized on the u-blox ZED-X20P (all-band), relative to perfect realization of the full model (`SEMANTICS.md`). Measured on firmware HPG 2.10 PROTVER 50.11 (2026-06-11, native USB). Vetted against the X20 HPG 2.10 interface description in `../gps-protocol-docs/u-blox/`. Perfectly-realized behavior is not listed.

## Capabilities and properties

- The fullest-featured receiver tested: `supports` carries band, fixed position and accuracy, raw output, RTCM MSM4/MSM7 and base ID, speed, and survey with accuracy and progress messages.
- Antenna cable delay, minimum elevation, and time GNSS realize requests exactly. Position quanta are the val-layer high-precision resolution, same as the F9P: fixed position 0.1 mm (ECEF and height), 1e-9 deg (LLH), accuracy 0.1 mm. Time pulse width quantized to 1 us.
- The as-found factory time grid is UTC, so the first probing run trips the --pps grid side effect in `BUGS.md` and reports itself not-left-as-found once (timeGNSS GPS is now set on this unit).

## Signals

The X20 has selectable signal plans (CFG-SIGNAL-PLAN: SP1, SP2, SP6 on this product); UBX-MON-GNSS reports the active plan's signals, which is what satpulse deduces as the supported set. The characterization therefore describes the active plan, not the silicon: configuration keys exist for Galileo E5b and BeiDou B2I, but they are not in this plan and are absent from the discovered set. satpulsetool does not expose plan selection.

Discovered supported set (active plan as shipped): GPS L1/L2C/L5, GAL E1/E5a/E6, BDS B1I/B1C/B2a/B3I, GLO L1/L2, QZSS L1/L1S/L2C/L5, NAVIC L5, SBAS L1.

- An enabled constellation must include an L1-band signal: selections without one are refused by the receiver (GPS L2C alone, GLO L2 alone, and every all-constellation band request that excludes L1 get a NAK). The accepted partial selections are exactly the L1 flavors: GPS L1, GAL E1, GLO L1, and BDS B1C+B1I.
- B1I and B1C enable together without complaint, confirming the M10's either-or constraint does not apply at PROTVER 50 (the firmware-version boundary in the `--gnss BDS` fix for issue #312).
- QZSS can be enabled only together with GPS (refused with BDS, GAL, or GLO alone), and SBAS only with at least one of GPS, GAL, or BDS (refused with GLO alone) - both exactly as the integration manual states. The same rules hold on the F9P and M10; the gen 8 M8T and the UM980 enforce no such coupling.
- NAVIC cannot be requested alone, but that is satpulsetool semantics, not the receiver: NAVIC, like QZSS and SBAS, cannot anchor a request (no non-augmentation major signal), so the tool refuses before the receiver is asked - even though the integration manual allows NavIC on its own on this receiver. NAVIC enables fine alongside the majors.
- Band-restricted requests drop constellations whose denoted set is empty (NAVIC on L1) rather than refusing.

## Message output

- RTCM 1005 (ARP) is requestable but not emitted while the receiver is in mobile mode, as on the F9P; the message carries the stationary reference position.
- SBAS MSM messages (1104/1107) are never emitted even with SBAS enabled and MSM4/MSM7 requested; u-blox receivers do not generate SBAS MSM.

## Testing notes

Native USB: no baud rate, immune to speed wedging, no session speed management. A default run takes about 5 minutes. The first-contact run's only failure was the known --pps grid side effect above. The vetted characterization is checked in at `baselines/ZED-X20P-HPG-2.10-PROTVER-50.11.json`.
