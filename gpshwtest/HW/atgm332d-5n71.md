# ATGM332D-5N71 (URANUS5 V5.3.0.0)

Single-band CASIC navigation receiver, V5 firmware. Characterized
2026-06-13 at 115200; baseline `URANUS5,V5.3.0.0.json`.

## Line budget at 9600

The unit ships at 9600, where its default NMEA load saturates the
line: responses lag by ~6 s or are lost, satpulsetool cannot read the
initial configuration, and characterization is impossible. The unit
attached here was therefore raised to 115200 persistently. Recipe
when the line is already saturated: free the line first - disconnect
the antenna (no fix shrinks the NMEA output to almost nothing) or
send the RAM-only `nmea-quiet` tag - then change speed, restore NMEA,
and save.

## Limitations relative to the model

- Identity: no hardware identity is reported (V5 has no MON-VER; the
  PCAS06 firmware query answers, the hardware query does not), so the
  receiver shows firmware only and the baseline slug has no model
  prefix.
- Signals: single-band, constellation-level selection only (CFG-NAVX
  navSystem): GPS L1 C/A, BDS B1I, GLONASS L1. No per-signal
  information exists (`sig` delivers nothing). A request that empties
  against this set writes navSystem 0, which the receiver
  ACKNOWLEDGES WITHOUT APPLYING - the configurator reads back the set
  actually in force.
- Leap second (`leap`): the whole MSG class (GPSUTC/BDSUTC) is
  acknowledged but never emitted (28-minute watch with both enabled
  at rate 1, more than two subframe-4 cycles, zero packets), so leap
  second information is not deliverable.
- Raw output (`obs`, `nav`) and RTCM output: acknowledged but never
  emitted / nonexistent; nothing is deliverable.
- Fixed position: stored as ECEF; an LLH request is realized by
  conversion, so the LLH form and height never read back (the
  position does, as ECEF).
- Time GNSS: GAL is not a valid time source (V5 predates Galileo
  support); a GAL request achieves GPS.
- Time pulse width quantized to 1 us.
- Active port: not identifiable, as on V6 (one CFG-PRT response per
  UART).
