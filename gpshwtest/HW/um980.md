# UM980 limitations (first contact)

How device-independent configuration is realized on the Unicore UM980, relative to perfect realization of the full model (`SEMANTICS.md`). Measured on firmware Build17548 (2026-06-10, UART-to-USB bridge at 115200). First contact: the generic probe path ran with no receiver-specific code, but the characterization is not yet baseline-quality - see the saturation incident below. Two satpulsetool defects found on this receiver are in `BUGS.md` (raw nav output requested at 1 Hz instead of ONCHANGED, which saturates the link; rtcmBaseID declared but absent).

## Solid findings (probed before the saturation incident)

- As-found state emits nothing periodically; all traffic in a capture is replies to the session's own queries (VERSION, MODE, 19-line CONFIG dump). The replies do not echo the query's message name, which is what forced the observation-window emissions filter.
- `--show-receiver` reports `supportedGNSS` as empty (the backend cannot deduce it yet), so signal probing falls back to the constellations enabled in the as-found configuration: GPS, GAL, GLO, BDS, QZSS.
- The backend does not implement `--show-port` yet (no `port`/`baudRate` fields), recorded in the characterization as a `showPort` limitation, not a failure. A `ConfigSupportFlags` entry declaring port reporting would let testers and users bound expectations; the receiver's CONFIG response carries the data an implementation would use.
- Antenna cable delay, minimum elevation, and time GNSS realize requests exactly.
- `rtcmBaseID`: behaves as a nonexistent property (set achieves nothing, readback omits it) although the backend declares support - see `BUGS.md`.
- Fixed position: latitude/longitude quantized to 1e-9 deg, ECEF coordinates to 0.1 mm, same resolutions as the ZED-F9P; height realizes exactly at the probed values.
- Fixed-position accuracy: always achieved as 0 whatever is requested. The backend does not declare `fixedPosAcc` support, so this is the bounded expectation, carried verbatim in the characterization.
- Time pulse width quantized to 1 us.

## Poisoned by the saturation incident

`--raw-out nav` saturated the link permanently (BUGS.md) and the disable could not get through, so everything after it in the run - PVT/satellite output probes, the message restore, and all of signal probing - ran against a flooded, lossy link. Apparent results from that phase (refusals, achieved-vs-readback disagreements, state lagging one request behind) are saturation artifacts, not receiver behavior; the same caution as the M8T's 9600-baud raw saturation applies: on a saturated link a reported error does not imply an unchanged configuration. Signal-set behavior and message output remain to be characterized after the satpulsetool raw-nav fix (or with the planned raised-speed session management, which would also make the flood survivable).

## Recovery procedure

When a run leaves the UM980 flooding (satpulsetool sessions fail with "no response to configuration probe message" while the port pours ephemeris messages): write `UNLOGALL\r\n` directly to the port at the session speed (hold the port open, drain, write, expect `$command,UNLOGALL,response: OK`). The as-found state emits nothing periodically, so UNLOGALL restores exactly the as-found message state; then re-enable the constellation set with `--gnss GPS,GAL,GLO,BDS,QZSS` and verify with `--show-config` plus a quiet capture.

## Second sweep (raw probing last)

With raw output probed last and signal probing moved ahead of it, a full sweep now collects clean signal and message data. New findings:

- The raw-nav flood is recoverable in-band after all: the `--raw-out none` disable times out once and succeeds on the retry, so the run completes and the receiver is left as found. The 1 Hz ephemeris request (BUGS.md) still makes this a coin toss on a 115200 line; treat the `UNLOGALL` procedure above as the fallback.
- `--reload` is realized as the Unicore `RESET` command: the receiver reboots and is silent for several seconds. Speed rediscovery now repeats its sweep after a settle to catch the receiver coming back.
- Signal-set readback misreports QZSS L5 as enabled when it is masked - a satpulsetool alias-table gap, see `BUGS.md`. Until fixed, every band-subset signal case involving QZSS reports a reported-vs-readback failure.
- The signal characterization is collected and vetted: the discovered supported set matches Unicore signal group 1 exactly. The baseline is checked in at `baselines/UM980-Build17548.json` (consecutive sweeps byte-identical). Like the M8T baseline, it deliberately carries the bug-shaped entries (the QZSS L5 readback values); the baseline diff after the alias fix is the signal to re-vet. Disruptive coverage (saves, resets, speed) has not yet been run on this receiver, so the baseline carries no baudRate/saveGranularity entries yet.
