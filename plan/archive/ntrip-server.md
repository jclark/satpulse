# NTRIP server: `stream.push` to remote caster (#238)

Push RTCM data from the GPS receiver to a remote NTRIP caster
using the NTRIP server (SOURCE) protocol.  Implemented as a
`stream.Push` instance in `gps/app/stream`.  Related: #126 (NTRIP).

The implementation should mirror `Pull` closely.  Reuse the same
`State` callback model (`Connecting`, `Connected`,
`Reconnecting`), `backoff`, and `pruningQueue`.  Do not add a
second RTCM observability path; `plan/rtcm-obs.md` handles
receiver-direction RTCM from the main dispatch process.

## Protocol

This plan implements the NTRIP v1 server (SOURCE) protocol.

An NTRIP "server" is a source of GNSS correction data that uploads
to a caster.  The protocol is:

1. Open a TCP connection to the caster.
2. Send a v1 SOURCE request:

```text
SOURCE <password> /<mountpoint>\r\n
Source-Agent: NTRIP satpulse/<version>\r\n
STR: <sourcetable-entry>\r\n
\r\n
```

3. Do not send `Ntrip-Version`.
4. If `STR` is not configured, omit the `STR:` line.
5. Read the response line from the caster.
6. Treat `ICY 200 OK` as success.
7. Treat any `ERROR ...` response, or any other response line, as
   failure.
8. After success, write raw payload bytes to the socket with no
   HTTP framing or chunked encoding.  The payload is typically RTCM
   but may be any format -- see the Configuration section.
9. If the connection drops, reconnect and repeat the full
   handshake.

## Configuration

```toml
[ntrip]
country = "THA"          # used as STR-record default for stream.push too
# (caster fields -- lat, lon, generator, formatDetails, etc.;
# may have no [[ntrip.mountpoint]] entries if no caster is wanted)

[[stream.push]]
ntrip.address = "caster.example.com:2101"
ntrip.mountpoint = "MY_BASE"
ntrip.password = "secret"
ntrip.description = "Bangkok"   # default = ntrip.mountpoint
ntrip.bitrate = 4800            # default = [ntrip].bitrate
```

`stream.push` is a table array so one receiver can push to multiple
destinations.  Transport is selected by which dotted keys are
present, matching the `stream.pull` style.  Initially only
`ntrip.*` is implemented; a future plain TCP push can use
`tcp.address`.

NTRIP server authentication uses a password only (see Protocol
section above).

The SOURCE upload's `STR:` header is generated by the closure
returned by the implemented `ntrip.StreamRecordBuilder` in
`gps/app/ntrip` **only when `protocol = "RTCM"`**.  The closure
uses the `[ntrip]` section's embedded `ntrip.SharedStreamConfig`
for global STR fields (country, lat, lon, generator,
formatDetails, etc.), this `[[stream.push]]` entry's embedded
`ntrip.StreamConfig` for `ntrip.description` and `ntrip.bitrate`,
and this entry's `ntrip.msm7to4` boolean when deciding whether
to substitute MSM7 message numbers with MSM4 numbers in field 5.
The closure returns "fields 3..n" of the STR record -- exactly
what the v1 spec requires for the SOURCE upload's `STR:` header.

For non-RTCM payloads (e.g. `protocol = "UBX"`), the STR header
is **omitted**.  Rationale: the closure hardcodes field 4
(`<format>`) to `"RTCM 3.3"` and synthesises field 5
(`<format-details>`) as RTCM message numbers.  Both are wrong
for non-RTCM streams.  The v1 spec makes the STR header
optional, and the v2 spec (§6.3.2 "Other Formats")
explicitly puts proprietary/raw payloads "beyond the scope of
this document," with no defined STR conventions.  Skipping the
header is the honest choice; the remote caster has its own
source-table entry and decides what to publish to clients
anyway.

The daemon implements this by leaving `NtripDestination.STR =
""` for non-RTCM push entries; `NtripDestination.Connect`
already omits the `STR:` header when `STR` is empty.

### Options

- `protocol` selects which packet format is forwarded.
  Transport-agnostic field, lives at the `[[stream.push]]` top
  level (not under `ntrip.*`).  Typed as `gpsreg.Protocol`,
  which already implements `encoding.TextUnmarshaler` and
  accepts the registered protocol names (currently `"RTCM"`,
  `"NMEA"`, `"UBX"`).  Future additions (e.g. SPARTN) just
  need a tag and packet format registered in the relevant
  package -- no plan-level change.

  When unset, the default is chosen by the configured transport,
  not by a global constant: NTRIP push defaults to `"RTCM"`
  because that is the typical NTRIP payload, but NTRIP itself is
  just a TCP transport with a header and does not constrain
  payload format -- SPARTN corrections, UBX diagnostics, etc.
  are legitimate uses if the operator sets `protocol`
  explicitly.  A future TCP push would supply its own default
  (or require an explicit value).
- `ntrip.msm7to4` converts MSM7 packets to MSM4 before writing.
  Only meaningful when `protocol = "RTCM"`; setting both `msm7to4
  = true` and a non-RTCM `protocol` is a config error.
- `ntrip.description` and `ntrip.bitrate` come from the embedded
  `ntrip.StreamConfig` struct.  `ntrip.msm7to4` is a separate
  field on `NtripPushConfig`, mirroring the caster's separate
  `MountConfig.MSM7to4` field.

The daemon checks each push entry's protocol tag against the
vendor's packet formats (`cfg.GPS.CreatePacketFormats()`) at
startup.  If the tag is absent (e.g. `protocol = "UBX"` on a
non-u-blox receiver) the entry is skipped with a warning rather
than failing the daemon: time/PHC sync is independent of push,
so a misconfigured push should not block startup.  `Push.Run`
takes the protocol tag (`gpsprot.Tag`) directly and filters
packets by `pkt.Tag()`; no `PacketFormat` slice needs to be
plumbed through.

## Destination

Lives in `gps/app/stream` alongside `Pull`.

Push gets its own `Destination` interface, parallel to `Pull`'s
existing `Source` interface but distinct.  Pull's `Source` returns
`io.ReadCloser` (so its `NtripSource.handshake` can splice
buffered read-ahead bytes back in front of the body via
`io.MultiReader`); Push's `Destination` returns `net.Conn` because
it only writes after the handshake and never has to recover
buffered prefix bytes.  The two interfaces share the same shape
but no implementation, so unifying them would force a rewrite of
Pull's working handshake for no real reuse.  Keep them separate.

```go
type Destination interface {
    Connect(ctx context.Context) (net.Conn, error)
}

// PushConfig is one [[stream.push]] entry.
type PushConfig struct {
    Protocol gpsreg.Protocol `toml:"protocol"` // default chosen by transport
    Ntrip    *NtripPushConfig `toml:"ntrip"`
}

// NtripPushConfig is the operator-facing TOML for one NTRIP
// push destination.  It is a pure TOML decoder target -- every
// field maps directly onto a TOML key, and no derived data is
// stored on it.
type NtripPushConfig struct {
    Address    string `toml:"address"`
    Mountpoint string `toml:"mountpoint"`   // remote caster's mountpoint
    Password   string `toml:"password"`
    ntrip.StreamConfig                       // embedded: Description, Bitrate
    MSM7to4    bool   `toml:"msm7to4"`
}

// NtripDestination is the runtime input to Push.Run.  It carries
// only the fields that get written onto the wire during the v1
// SOURCE handshake, plus the address to dial.  Built once at
// startup from NtripPushConfig and the resolved STR string;
// stateless thereafter (Connect does not mutate it, so each
// reconnect re-runs the handshake from the same destination).
type NtripDestination struct {
    Addr       string // "host:port"
    Mountpoint string
    Password   string
    STR        string // fields 3..n of the STR record (without leading "STR;<mountpoint>;"); empty means omit the STR: header
    UserAgent  NtripUserAgent // populated by daemon from cmd.Version() at startup
}

func (d *NtripDestination) Connect(ctx context.Context) (net.Conn, error)
```

`NtripUserAgent` is the type already used by `NtripSource`
(pull) -- the prerequisite rename commit (see Prerequisites)
gives it its mixed-case spelling.  Push reuses the same type
and the same lower-case `satpulse` product token used by pull's
`User-Agent` and the caster's `Server` header; there is no reason
for them to differ.  The daemon populates `UserAgent.Version`
from `cmd.Version()` so `gps/app/stream` does not import the cmd
package.

The naming follows the Ntrip specs (mixed case "Ntrip" for
identifiers; the literal "NTRIP " wire prefix in Source-Agent
(server upload) and Server (caster response) headers is per
Appendix B of the v1 spec and is unchanged).

A future plain-TCP push would add a `TcpDestination` that
satisfies `Destination`; it parallels Pull's `TCPSource` but
returns `net.Conn`.

The two types have non-overlapping jobs:

- `NtripPushConfig` is what `go-toml` decodes a
  `[[stream.push]].ntrip.*` block into.  Description and
  Bitrate get consumed by the `StreamRecordBuilder` closure at
  startup, and `MSM7to4` is copied into the `Push.Run` argument;
  the runtime never reads `NtripPushConfig` again.
- `NtripDestination` is what `Push.Run` calls `Connect` on.  It
  has the fields the SOURCE handshake actually needs and nothing
  else.

`Connect` does:

1. Dial TCP with `net.Dialer.DialContext`.
2. Write the v1 SOURCE request:
   - `SOURCE <Password> /<Mountpoint>\r\n`
   - `Source-Agent: NTRIP satpulse/<version>\r\n`
   - `STR: <STR>\r\n` if `STR` is non-empty
   - terminating blank line `\r\n`
3. Read the caster response line.
4. Return the raw `net.Conn` on success.
5. Close and return an error on rejection.

`d.STR` was computed at startup by the daemon calling the
implemented `ntrip.StreamRecordBuilder` closure with the matching
`NtripPushConfig`'s embedded `StreamConfig`, mountpoint name,
`hasAuth = false`, and `MSM7to4` value.  No NTRIP-package helpers
are invoked at connect time.

The caller only sees a connected stream socket, same as
`Pull.reader` only sees a connected source socket.

Success is exactly `ICY 200 OK`.  Any `ERROR ...` response, or any
other response line, is a failure.  After success, the connection
switches immediately to raw RTCM byte streaming; there is no HTTP
message body or chunked framing.

## Push

Unlike `Pull`, `Push` does not own a packet bcast.  It consumes the
receiver's existing packet bcast, because that is already the single
source of truth for observability and downstream readers.

The pipeline has three stages, with the reconnect loop on the writer
side rather than the reader side:

1. **Subscriber/filter stage**
   Subscribe to the receiver packet bcast and receive scanned
   packets from it.  Discard packets whose format does not match the
   configured protocol filter.
2. **Pruning queue**
   Reuse the same `pruningQueue` as `Pull` so a slow or disconnected
   network link collapses old packets to the latest packet per RTCM
   message type, with the same MSM multiple-message handling.
3. **Writer/reconnect stage**
   Own the outbound network connection, reconnect with adaptive
   backoff, and write queued packets to the remote caster.

```go
type Push struct{}

func NewPush() *Push

func (s *Push) Run(ctx context.Context, lg *slog.Logger,
    packets *bcast.Bcast[scan.Packet],
    dest Destination,
    pktFormats []gpsprot.PacketFormat,
    msm7to4 bool,
    onState func(State, error)) error
```

`Push.Run` blocks until `ctx` is cancelled or the input bcast is
closed.  Unlike `Pull`, there is no serial writer whose failure is
fatal to the daemon; outbound network failures are handled as normal
reconnect events.

## Run

`Run` follows the same structure as `Pull.Run`:

1. Create an internal context as a child of `ctx` via
   `context.WithCancel(ctx)`, with `defer iCancel()`.  Two cancel
   paths feed it: parent ctx cancellation (via the parent-child
   relationship) and the queue calling `iCancel` when the input
   bcast closes.  The writer watches `iCtx` only and doesn't need
   to know which path triggered cancellation -- both proxy
   (`time/internal/proxy/proxy.go connWriteWorker`) and caster
   (`gps/app/ntrip/caster.go streamLoop`) already treat bcast
   close as a first-class shutdown signal alongside ctx
   cancellation; Push needs the queue->writer bridge because its
   queue sits between the bcast subscriber and the writer, so the
   writer cannot watch the bcast directly.
2. Subscribe to the input bcast before starting worker goroutines.
3. Create a queue output channel `qCh`.
4. Create a reconnect notification channel `reconnectCh` with
   buffer size 1.  See "Reconnect notification" under Writer for
   why.
5. Start the queue goroutine, passing `iCtx` and `iCancel`.
6. Start the writer goroutine, passing `iCtx`.
7. Wait for both goroutines to exit.
8. Return `nil` if `ctx.Err() == nil` (input bcast closed cleanly)
   or `ctx.Err()` otherwise (parent ctx cancelled).  No
   non-reconnect fatal error path exists for Push: outbound
   network failures are handled as normal reconnect events.

No internal `Packets` bcast is needed on `Push`, because packets are
already broadcast by the main receiver scan path.

## Queue

The queue should use the same `pruningQueue` implementation as
`Pull`, not a new variant.

The queue differs from `Pull.queue` in three ways:

1. The queue input is the receiver subscription channel rather than
   `Pull`'s internal broadcast.
2. Reconnect notifications come from the writer rather than the
   reader.
3. The queue must watch `iCtx.Done()` itself, and on `subCh`
   close it must call `iCancel` to wake the writer.  Pull's
   queue can rely on `subCh` closing on shutdown because Pull
   owns its bcast and closes it as part of its shutdown chain,
   and `bcast.Unsubscribe` does not close the subscriber channel
   (verified in `gps/app/bcast/bcast.go`).  Push does not own
   the receiver bcast, and the writer is often blocked in
   `Connect` or backoff sleep -- it cannot observe `qCh`
   closing.  Translating "bcast closed" into `iCtx`
   cancellation is what bridges the queue to the writer; this
   matches how proxy and caster handle bcast close as a clean
   shutdown signal.

```go
func (s *Push) queue(iCtx context.Context, iCancel context.CancelFunc,
    packets *bcast.Bcast[scan.Packet],
    subCh <-chan scan.Packet,
    reconnectCh <-chan struct{},
    writerCh chan scan.Packet,
    pktTag gpsprot.Tag)
```

`writerCh` is bidirectional rather than send-only because the
queue also drains it on reconnect (see step 4).  The queue is
its sole sender, so a non-blocking receive is safe.

The queue does the following:

1. Receive packets from `subCh`.
2. Ignore packets whose tag does not match `pktTag` or whose
   checksum is not valid.  The checksum filter matches the
   caster's policy in `gps/app/ntrip/caster.go` (don't forward
   garbage).
3. Enqueue matching packets using `pruningQueue`.
4. On `reconnectCh`, the writer just hit a write error, so the
   in-flight pipeline state may already reflect a partial send
   on the broken connection.  Drop everything outside the
   pruning queue: drain `writerCh` non-blockingly, set
   `outCh = nil` to discard the staged `front`, call
   `q.reconnect()` to bump the MSM epoch, and re-pull a fresh
   front from `q` if any items remain.  This is best-effort:
   packets that subCh delivers between the writer's failure and
   the queue picking `reconnectCh` are enqueued under the old
   MSM epoch and remain in `q` until evicted by a fresh
   same-msgID packet.  A small bounded number of pre-disconnect
   packets may therefore still be written after reconnect.
   Eliminating that race would require either an unbuffered
   `writerCh` plus a readiness handshake, or a synchronous
   reset RPC from writer to queue; the additional complexity
   isn't justified for a live stream where staleness self-heals
   within ~1 second under normal RTCM rates.
5. On `subCh` close, call `iCancel` to cancel the internal ctx
   so the writer wakes up regardless of whether it is in
   `Connect`, in backoff sleep, or in the streaming write loop.
   Then discard any remaining queued packets, close `writerCh`,
   call `packets.Unsubscribe(subCh)`, and return.
   `bcast.Unsubscribe` is a no-op if the bcast is already
   closed, so calling it is safe.
6. On `iCtx.Done()` (parent ctx cancellation), do the same
   cleanup as step 5 except for the `iCancel` call (already
   cancelled).

This is the minimum change needed to reuse Pull's queue logic
without inventing a separate packet type just for reconnect
markers.

The drain-on-reconnect in step 4 collapses the two most likely
sources of post-reconnect staleness (the 1-slot `writerCh`
buffer and the staged `front`).  It does not guarantee strict
"latest per message type" output on the new connection -- see
step 4 for the residual race.  This is deliberate; the simpler
design beats the small staleness window in practice.

## Writer

The writer owns the outbound reconnect loop, analogous to how
`Pull.reader` owns the inbound reconnect loop.

```go
func (s *Push) writer(ctx context.Context, lg *slog.Logger,
    dest Destination,
    qCh <-chan scan.Packet,
    reconnectCh chan<- struct{},
    msm7to4 bool,
    onState func(State, error)) error
```

The writer does the following:

1. Call `onState(Connecting, nil)` before the first attempt.
2. Connect using `dest.Connect(ctx)`.
3. On connect failure:
   - log
   - increase backoff
   - call `onState(Reconnecting, err)`
   - sleep for `b.delay()` unless cancelled
   - call `onState(Connecting, nil)` before retrying
4. On success:
   - decrease backoff
   - call `onState(Connected, nil)`
   - enter a write loop consuming `qCh`
5. For each queued packet:
   - optionally convert MSM7 to MSM4
   - call `conn.SetWriteDeadline(time.Now().Add(writeTimeout))`
     before each write (see "Write deadline" below)
   - write raw bytes to `net.Conn`
6. On write error (including `i/o timeout`):
   - close the connection
   - notify `reconnectCh` via a non-blocking send (see
     "Reconnect notification" below)
   - return to the outer reconnect loop
7. On `qCh` close:
   - close the connection
   - return nil

### Reconnect notification

`reconnectCh` is a buffered (size 1) `chan struct{}`.  The
writer signals it after a write error so the queue calls
`q.reconnect()` to advance the MSM epoch and prevent dedup
from spanning a broken connection.  The send is non-blocking:

```go
select {
case reconnectCh <- struct{}{}:
default:
}
```

The non-blocking pattern handles three cases that an unbuffered
blocking send would hang on:

- The queue is busy in another select arm.  One pending signal
  is enough; if the buffer already has one, the duplicate is
  harmless because `q.reconnect()` is idempotent (advancing
  `msmEpoch` twice has the same effect as advancing it once).
- The queue has exited via the `subCh`-close path (see Queue
  step 5) and is gone.  The send drops cleanly instead of
  blocking forever.
- A race between the writer's write-error handling and the
  queue's exit during shutdown.

This is the standard Go idiom for "wake up the consumer; one
queued wake-up is enough."

### Write deadline and ctx-watcher

A dead remote can leave the TCP connection "established" forever
(no RST/FIN, kernel send buffer fills, then `Write` blocks until
TCP keepalives expire -- default 2 hours on Linux).  Without a
deadline, the writer is stuck and `Push.Run`'s ctx alone won't
recover the loop because `Write` is blocked in syscall.

Two independent mechanisms cover this:

- **Per-write deadline.**  Before each `conn.Write`, call
  `conn.SetWriteDeadline(time.Now().Add(writeTimeout))`.  On
  `i/o timeout`, the writer treats it as a normal write error
  (close conn, signal `reconnectCh`, reconnect).  This is the
  *correctness* mechanism: a dead remote is detected within
  `writeTimeout`.  Default 30 s -- generous enough for transient
  hiccups, short enough that recovery is timely.
- **Ctx-watcher goroutine around the streaming phase.**  Same
  pattern `NtripSource.Connect` already uses for the handshake:
  a goroutine that calls `conn.Close()` on `ctx.Done()`,
  cancelled via a `done` channel when the writer exits the
  streaming phase normally.  This is the *latency* mechanism:
  ctx cancellation aborts an in-flight blocked write
  immediately instead of waiting up to `writeTimeout`.

Both are needed: the deadline alone allows shutdown to wait up
to `writeTimeout` (bad UX); the ctx-watcher alone doesn't help
when the daemon stays running but the network is dead (no ctx
cancel).

As with `Pull`, the backoff also decays while the connection stays
healthy.  Mirror Pull's pattern: track `lastDecay` and, after each
successful `conn.Write`, check `time.Since(lastDecay) >=
backoffDecay` and call `b.decrease()` if so.  RTCM writes happen at
~1 Hz on a healthy stream, so the check fires reliably without
needing a separate ticker or goroutine.

The reconnect path repeats the full v1 handshake each time: TCP
connect, SOURCE request, `ICY 200 OK` check, then raw data stream.

The packet the writer was mid-`Write` on when the socket breaks
is lost.  The queue's reconnect handler drops the staged
`front` and drains `writerCh` (see Queue step 4) so the new
connection starts from mostly-fresh pruned state; a small
bounded number of pre-disconnect packets may still slip through
under the race described in that step.  This is acceptable
because the stream is live and `q` self-heals within a few
packets as fresh updates supersede stale ones.

## MSM7 to MSM4 conversion

Use the same policy as the implemented NTRIP caster:

- only attempt conversion for RTCM MSM7 packets
- on parse/convert/serialize failure, log at debug/warn level and
  send the original packet unchanged

Conversion belongs in the writer, immediately before `conn.Write`,
so the queue stays keyed on the original scanned packet and remains
identical to `Pull`.

## Daemon integration

### Config and schema work

`time/app/daemon.Config` already has `Stream stream.Config`, so
the remaining config work is specific to `stream.push`:

- add `Push []PushConfig` to `stream.Config`;
- add `NtripPushConfig` with address, mountpoint, password, an
  embedded `ntrip.StreamConfig`, and its own `MSM7to4 bool`
  field;
- update `configs/config-schema.json` to describe
  `[[stream.push]]`, including `protocol`, `ntrip.*`, and the
  rule that `ntrip.msm7to4` is valid only for RTCM pushes.

`Config.hasNtripStream()` in `time/app/daemon/config.go` must be
extended (its comment already anticipates this) to return true
when *either* caster mountpoints exist or any `[[stream.push]]`
entry uses `ntrip.*` with `protocol = "RTCM"`.  This drives
`cfgNtripStream` in `gps.go`, which sets `target.Get |=
PropIDSignalsEnabled | PropIDMode` so STR-record building has
signals and mode available; otherwise those fields fall back to
placeholders.  Non-RTCM pushes omit the STR header entirely (see
Configuration) and do not need this receiver state, so they are
deliberately excluded from the predicate.

### Caster

`startNtrip` (in `time/app/daemon/ntrip.go`) is unchanged.  It
continues to bail when `len(cfg.Ntrip.Mountpoint) == 0` and to
build a single `StreamRecordBuilder` closure, calling it once per
mountpoint with that mountpoint's `hasAuth` value (`m.Auth !=
nil`) and `MSM7to4` value.  No restructuring; push wiring lives
elsewhere.

### Push

Push setup lives in the daemon's stream wiring (alongside
`stream.pull`, likely in `time/app/daemon/stream.go`).  It is
independent of `startNtrip` -- the two share GPS state inputs but
build their own `StreamRecordBuilder` closures.

1. If no `[[stream.push]]` entry uses `ntrip.*`, return nil.
2. If any NTRIP push entry has `protocol = "RTCM"` (the
   default), build a `StreamRecordBuilder` closure with
   `configCapturePos = cc.pos`, the same opportunistically
   captured `PosGeoMsg` already used by the caster's STR-record
   builder as a lat/lon fallback.  Skipped entirely if all NTRIP
   push entries are non-RTCM.
3. For each NTRIP push entry, construct an `NtripDestination`
   with the address, mountpoint, password, and `UserAgent`
   (built from `cmd.Version()`) copied from `NtripPushConfig`
   plus daemon state.  For `protocol = "RTCM"` entries, also
   call the closure with the entry's `StreamConfig`, mountpoint
   name, `hasAuth = false` (see "Push STR field 16" below), and
   `MSM7to4`, then store the result in `NtripDestination.STR`.
   For non-RTCM entries, leave `STR = ""` so `Connect` omits the
   `STR:` header (see Configuration above for rationale).
4. Start each `Push.Run` in its own goroutine via `wg.Go`, with
   an `onState` callback that logs destination-specific state
   changes.

The receiver packet bcast already exists in the daemon and is
reused; no extra dispatcher channel and no RTCM event generation
is added on the push path.

### Push STR field 16

The Ntrip v1 and v2 specs both define field 16
(`<authentication>`) as "access protection for this particular
data stream" -- describing how *clients* of the caster serving
this stream must authenticate.  For caster mountpoint STR
records this is well-defined (we know our own user list).  For
the STR string sent in the SOURCE/POST upload to a remote
caster, this is information only the remote caster can know;
the spec is silent on how the server is supposed to populate
it.

We always send `N` (no authentication) for push.  Rationale:

- The server has no defensible way to know the remote caster's
  client-auth policy.
- The remote caster owns its own source-table entry and uses it
  when publishing to clients; the STR header we send during
  upload is hint-only metadata.
- Sending any value derived from our own caster's per-mountpoint
  auth would be actively misleading and could make the remote
  caster advertise wrong information to its clients if it trusts
  our STR string verbatim.

This is implemented by calling the `StreamRecordBuilder` closure
with `hasAuth = false` for every RTCM push entry, regardless of
the caster's own per-mountpoint auth settings.  No new
operator-facing config is added.

## Testing

- Unit test `NtripDestination.Connect` using a local TCP listener that
  verifies the exact v1 handshake:
  - `SOURCE <password> /<mountpoint>`
  - `Source-Agent` begins with `NTRIP satpulse`
  - no `Ntrip-Version` header
  - `STR: ...` present when `d.STR` is non-empty (RTCM payload)
    and omitted when `d.STR` is empty (non-RTCM payload or no
    STR record synthesised)
- Unit test success response handling: `ICY 200 OK`.
- Unit test error response handling: `ERROR - Bad Password`,
  `ERROR - Mount Point Taken or Invalid`, and unexpected response
  lines.
- Unit test the queue with reconnect notifications, especially the
  MSM multiple-message boundary behavior.
- Unit test writer reconnect behavior with a listener that accepts a
  connection, reads a few packets, then closes the socket.
- Unit test bcast-close shutdown path: input bcast closes while the
  writer is mid-`Connect` or mid-backoff-sleep (caster down /
  unresponsive listener); verify the queue calls `iCancel`, the
  writer's ctx wakes, and `Push.Run` returns `nil`.
- Unit test `reconnectCh` non-blocking send: provoke a write error
  while the queue has already exited; verify the writer does not
  block on the send.
- Unit test write deadline: listener accepts the SOURCE handshake
  but never reads body bytes (TCP send buffer fills); verify the
  writer hits `i/o timeout` within `writeTimeout`, closes the conn,
  and reconnects.
- End-to-end test: feed RTCM packets into a `bcast.Bcast`, run
  `Push`, and verify the remote test server receives the expected
  stream after reconnects.
